Why not just use a list?

  • A list lets you take any item: items[3], items.remove("x")
  • Some data must come out in a strict order, or things break
  • Undo in the wrong order would undo your first change, not your last
  • A stack or queue restricts how items go in and come out

Don't ask "which item do I want?" Ask "which item is next, by the rules?"

The plan: Why these exist: they take away freedom on purpose, so data always comes out in the right order.

Say: "The rule is the feature. If the code can't grab an item from the middle, nobody can break the order by mistake."

Inside, both are still a normal Python list. The class just hides it and gives you only the allowed moves.

A stack: last in, first out (LIFO)

Also called FILO: first in, last out. Like a stack of plates: you only touch the top.

  • Undo / redo
  • The call stack (Python tracks function calls this way)
  • Backtracking (a maze: go back to the last fork)
  • Syntax parsing (does every ( have its )?)

Push on the top, pop off the top. Nothing else.

The plan: What a stack is: you only ever add to and take from the top.

Point at the picture: "addTop puts a value on the pile. rmTop takes the top one off. The middle and the bottom can't be reached."

Say: "Two names for the same rule: LIFO, last in first out, and FILO, first in last out. The curriculum uses FILO."

The common words are push (add on top) and pop (take off the top). The curriculum's methods are addTop and removeTop; the homework uses push and pop.

The plan: We write stacks.py: a Stack class with addTop, removeTop and peek. Then undo.py uses it as an undo history.

TYPE THIS, in order

stacks.py · part 1: the class

class Stack:
    def __init__(self):
        self._items = []

part 2: addTop (inside the class, 4 spaces)

    def addTop(self, item):
        self._items.append(item)

part 3: removeTop

    def removeTop(self):
        if not self._items:
            raise Exception("Stack is empty")
        return self._items.pop()

part 4: peek

    def peek(self):
        if not self._items:
            raise Exception("Stack is empty")
        return self._items[-1]

part 5: a new file, undo.py

from stacks import Stack

history = Stack()
history.addTop("type Hello")
history.addTop("make it bold")
history.addTop("change the colour")
print(history.peek())
print(history.removeTop())
print(history.peek())

A queue: first in, first out (FIFO)

Like a coffee shop line: join at the back, get served from the front. Nobody skips.

front →
Maria

← back
  • addRight joins at the back (right) · removeLeft serves the front (index 0)
  • Task scheduling and request handling (in the order they arrive)
  • Message brokers (messages wait their turn) · Breadth-first search

A queue is fair: the oldest item always goes next.

The plan: What a queue is: add at the back, take from the front, so the oldest item always goes next.

Point at the boxes: "This is the Python list inside our Queue. Index 0, Maria, is the front of the line. New people join on the right."

Common words: enqueue (join the line) and dequeue (leave the front). The curriculum calls them addRight and removeLeft; the homework uses enqueue and dequeue.

queues.py · part 1: the class

class Queue:
    def __init__(self):
        self._items = []

part 2: addRight

    def addRight(self, item):
        self._items.append(item)

part 3: removeLeft

    def removeLeft(self):
        if not self._items:
            raise Exception("Queue is empty")
        return self._items.pop(0)

part 4: peek

    def peek(self):
        if not self._items:
            raise Exception("Queue is empty")
        return self._items[0]

  • pop() takes the last item: nothing moves, O(1)
  • pop(0) takes the first item: n − 1 items move, O(n)
  • We use pop(0) on purpose: it keeps the queue easy to read. Real code uses collections.deque and popleft(): O(1)

Same answer, different cost. Fine for 10 people, slow for a million.

The plan: Why pop(0) is slow: removing the first item makes every other item move one seat. We keep it anyway, to keep the class simple.

Point at the red box: "Maria leaves. A Python list has no empty seats, so Sam, Alex and Jo each move left. With a million people, that's a million moves to serve one person."

A deque ("deck") is a double-ended queue: fast to add or remove at both ends.

How slow is pop(0)? Time it speed.py

The plan: We write speed.py: empty a long line with pop(0), then with a deque, and time both.

** CODE ALONG, about 3 minutes. ** New file speed.py. Students can watch instead of typing.

TYPE THIS, in order

speed.py · part 1

import time
from collections import deque

for n in [25_000, 50_000, 100_000]:
    line = list(range(n))
    start = time.perf_counter()
    while line:
        line.pop(0)
    slow = time.perf_counter() - start

part 2 (still inside the for, 4 spaces)

    line = deque(range(n))
    start = time.perf_counter()
    while line:
        line.popleft()
    fast = time.perf_counter() - start
    print(f"{n:>7} people   pop(0): {slow:.3f}s   popleft: {fast:.3f}s")

Ctrl+S, then:

python3 speed.py
  • 25_000: the underscore is just for reading, like a comma. time.perf_counter() is a stopwatch in seconds.
  • while line: runs until the line is empty (an empty list is False).
  • {slow:.3f} prints 3 decimals. {n:>7} lines the numbers up.
  • Say: "Seconds change from laptop to laptop. Look at the pattern: double the people, and pop(0) takes about 4 times as long. popleft barely moves."
  • Why 4×: n people each cost about n moves → n × n. Twice the people → 4 times the work (the Big-O lecture's O(n²)).
  • The slide runs Python in the browser, so it's slower than a laptop. Real laptop numbers: see the RUNBOOK.
